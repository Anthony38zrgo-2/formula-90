1. PROJECT OVERVIEW / ARCHITECTURE
================================================================================
- Simulation core is Rust (`game/sim` crate `game_sim`, depends on
  `vehicle_physics_engine` crate in `game/physics/engine`). It is the SINGLE
  authoritative simulator (snapshot-server model): one simulator, no divergence
  between headless and in-engine.
- A minimal C++ Godot bridge (`native/src/sim/f90_sim_bridge.cpp`) loads
  `game_sim.dll` and drives the real `F194RustVehicle` (GDExtension C++ node in
  `native/src/vehicle/f1_94_rust_vehicle.cpp`, script wrapper
  `game/addons/formula90s/scripts/f1_94_rust_vehicle.gd` + `f1_94_rust_input_controller.gd`).
- gdext is NOT used (Godot 4.7.1 has no `extension_api-4-7.json`), so the bridge
  is hand-written C++ talking to Rust via a C-ABI (`game/sim/src/c_abi.rs`,
  mirrored in `native/include/formula90s/sim/f90_sim_bridge.h`).
- Drive path (the stable one): bridge calls `sim_world_solve_external` (core
  returns world-space force+torque via `solve_external`), then applies it with
  Godot `apply_central_force`/`apply_torque`. Gravity is left to Godot
  (`set_bridge_controlled` sets `gravity_scale=1.0`; core excludes gravity).

   Chosen scope: "Full keymap extraction (Recommended)".

ROOT CAUSE (diagnosed, read-only confirmed):
- The KEYMAP ITSELF IS FINE AND DECOUPLED ENOUGH. Actions live only in
  `game/project.godot -> [input]` (Throttle, Brakes, Steer Left/Right, Handbrake,
  Clutch, Shift Up/Down, aid_1..5, ui_back_to_menu, ShowDebug). The active
  controller `F194RustInputController.gd` reads them BY NAME. There is NO runtime
  re-registration of InputMap anywhere. The "gears stuck on 1st" is NOT a keymap
  problem.
- THE REAL BUG IS IN THE BRIDGE GLUE (the "godot acopled thing"):
  `F90SimBridge::drive_integrate` calls `fn_solve_external_` with HARDCODED
  `clutch = 0.0, gear_request = 0, toggle_tc = false`. So the vehicle's
  `gear_request_` (set by the input controller) is NEVER forwarded to the core.
- The core's powertrain only shifts when `input.gear_request` is `Some(req)`
  (`game/physics/engine/src/powertrain.rs:135`). With `None` (because
  `gear_request=0 -> None` in c_abi), `desired` stays at `current_gear` -> STUCK
  IN GEAR 1.
- Secondary sentinel bug: c_abi maps `gear_request == 0 -> None`, but core
  contract `types.rs:539` says `Some(0)=Neutral`, `Some(-1)=Reverse`,
  `None=no change`. So requesting NEUTRAL is currently impossible (collides with
  no-change). The C++ vehicle uses `-2` as its "no request" sentinel
  (`f1_94_rust_vehicle.cpp:110`).
- Evidence the controller side works: `F194RustInputController.gd` reads
  Shift Up/Down, computes next gear, calls `vehicle.set_gear_request(n)`.
  The vehicle stores it (`gear_request_`, default -2) and syncs `current_gear_`
  from core telemetry every frame (`f1_94_rust_vehicle.cpp:1218`). The break is
  purely that the bridge path (`drive_integrate`) ignores it.
