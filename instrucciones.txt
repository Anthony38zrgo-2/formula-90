# Handoff — Mejoras de desacoplamiento y robustez de build (Formula90s)

Este documento es un handoff detallado del análisis y el plan de mejoras
derivado del incidente: "audio V10 silencioso + 7ª marcha no disponible"
en el coche f1_2026_2008. El objetivo es evitar que errores de este tipo
(DESINCRONIZACION de SHA/BUILD, constantes hardcodeadas, validacion
enganosa, acoplamiento entre capas) vuelvan a ocurrir con frecuencia.

================================================================================
0. CONTEXTO / INCIDENTE RAIZ
================================================================================

Sintomas:
  - El audio del V10 no sonaba en absoluto.
  - La 7ª marcha no estaba disponible (el coche solo subia hasta 6ª).

Causa raiz del AUDIO:
  - Desincronizacion de res://BUILD_SOURCE. El DLL compilado lleva embebido
    FORMULA90_BUILD_SHA = git rev-parse HEAD = 6d862847e5b8466267a25be907f168acfe94fce3,
    pero game/BUILD_SOURCE contenia d7d8a08fca460341cf1591f508bd58be4c7d1c14 (SHA viejo).
  - El gate de F90Core::load_dll (f90_core.cpp:221) fallaba con:
      FATAL: native BUILD does not match recorded source.
      Native=6d862847... recorded=d7d8a08f...
  - Eso hacia que el facade NUNCA se inicializara -> cero audio.
  - El coche se movia porque F194RustVehicle tiene fisica legacy propia,
    pero sin F90Core no hay cadena de audio.

Causa del BUG de 7ª:
  - Cap hardcodeado `current_gear < 6` en f1_94_rust_input_controller.gd.
  - YA CORREGIDO a data-driven leyendo gear_ratios.size() del JSON.

Fix YA APLICADO (parche temporal):
  - game/BUILD_SOURCE escrito con el HEAD actual.
  - build_windows.ps1 ahora regenera BUILD_SOURCE al inicio del build.
  - Esto desbloquea, pero NO PREVIENE que vuelva a desincronizarse.

================================================================================
1. HALLAZGOS CLAVE (EVIDENCIA)
================================================================================

  - F90Core            native/src/core/f90_core.cpp:212-224
                       (mismatch -> return false, early return) + 2a comprobacion :280-285
  - VehicleAudio...    native/src/presentation/vehicle_audio_controller_native.cpp:115-127
                       (mismatch -> return false) + :185-190
  - F194RustVehicle    native/src/vehicle/f1_94_rust_vehicle.cpp:286-288

  - SConstruct:10-13                       -> C++ (libformula90s)

================================================================================
2. PLAN DE MEJORAS
================================================================================

--------------------------------------------------------------------------------
P0 — INTEGRIDAD DE BUILD (CRITICO: previene la recurrencia exacta)
--------------------------------------------------------------------------------

P0.1 Fuente unica de SHA via env-var  (ENFOQUE ELEGIDO)
  - scripts/build_windows.ps1:
      Calcular UNA vez:  $sha = (git rev-parse HEAD).Trim()
      Exportar:          $env:FORMULA90_BUILD_SHA = $sha
      ANTES de invocar SCons y cargo.
  - SConstruct:10-13:
      Leer FORMULA90_BUILD_SHA del entorno si existe; si no, git rev-parse HEAD.
  - formula90-core/build.rs:4-15  y  vehicle-audio-engine/build.rs:4-15:
      Leer std::env::var("FORMULA90_BUILD_SHA") primero; fallback a git.
  - (Opcional, consistencia) vehicle-physics-engine/build.rs:
      Alinear para usar el mismo SHA de 40 chars en f1_94_physics_build_sha().
  - RESULTADO: C++, los crates Rust y BUILD_SOURCE comparten un SHA identico
    e imposible de desincronizar. El gate runtime queda como backstop que
    nunca deberia dispararse.

P0.2 scripts/check_runtime_parity.ps1  (nuevo, pre-launch)
  - expected = git rev-parse HEAD
  - recorded = Get-Content game/BUILD_SOURCE (strip)
  - Assert expected == recorded  y  recorded.length() == 40.
    Con P0.1 esto garantiza que todos los DLL desplegados coinciden
    (porque se construyeron con ese mismo SHA).
  - (Opcional) Recalcular SHA256 del JSON de fisica de cada vehiculo y
    comparar con physics_sha256 de su manifest.json; fallar con mensaje
    accionable si difiere.
  - Llamar este script desde run_f1_94.ps1 y run_f1_94_no_rebuild.ps1
    ANTES de lanzar Godot.

P0.3 Arreglar -ValidateRuntimeOnly
  - Reemplazar el no-op (run_f1_94.ps1:210-213, run_f1_94_no_rebuild.ps1:187-190)
    por una llamada real a check_runtime_parity.ps1 (o al menos el assert
    HEAD==BUILD_SOURCE). Eliminar el mensaje enganoso "validado".

--------------------------------------------------------------------------------
P1 — DESACOPLAR GDSCRIPT DE LA CONFIG NATIVA
--------------------------------------------------------------------------------

P1.1 Exponer get_gear_count() / get_gear_ratios()
  - Anadir al FFI de F194RustVehicle (y/o F90Core) un getter que devuelva el
    nº de marchas del config cargado (el facade ya tiene el config).
  - El input controller usara vehicle.get_gear_count() en vez de re-leer/parsear
    el JSON: mantiene el beneficio data-driven pero elimina el duplicado de
    ruta/parseo. Conservar el fallback a JSON como red de seguridad.

P1.2 Autoridad unica de ruta de config
  - F90Core.config_json_path es la autoridad. En _ready del vehicle (o del
    F90Core), derivar physics_config_path del core cuando exista, eliminando
    la propiedad duplicada.
  - telemetry_manager.gd:21: reemplazar F1_94_PHYSICS_CONFIG hardcodeado por
    lectura de config_json_path del vehiculo/F90Core activo.

--------------------------------------------------------------------------------
P2 — ELIMINAR MAGIC STRINGS
--------------------------------------------------------------------------------

P2.1 Bank path
  - vehicle_audio_controller_native.cpp:198: sustituir el literal
    res://sounds/banks/v10_vehicle por la propiedad bank_dir compartida
    (igual que usa F90Core). Anadir propiedad bank_dir a
    VehicleAudioControllerNative que espeje la de F90Core.

P2.2 Nombre de bus constante
  - Definir const String VEHICLE_AUDIO_BUS = "Vehicle"; en un header
    compartido (o constante en .gd autoload) usado por ensure_vehicle_bus.gd,
    f90_core.cpp y vehicle_audio_controller_native.cpp.
  - Unificar el naming del nodo de escena ("VehicleAudio" -> algo coherente)
    para evitar confusion.

--------------------------------------------------------------------------------
P3 — SUPERFICIE DE ERRORES Y GUARDAS DE REGRESION
--------------------------------------------------------------------------------

P3.1 Unificar reporte de errores FFI
  - game-sim/src/c_abi.rs:117-120: en fallo de from_json_path, escribir
    err_buf + printerr en vez de return 0 silencioso.

P3.2 Log de skip de audio en headless
  - f90_core.cpp create_audio_nodes: cuando es headless,
    print("[F90Core] audio nodes skipped (headless)") para no parecer roto.

P3.3 Test de integracion cargo
  - Extender el test de vehicle-physics-engine para cargar cada JSON de
    vehiculo shipeado en game/data/vehicles/*/ y assert validate() pasa y
    gear_ratios.len() == traction_control_*.len().
    Detecta JSON obsoletos sin abrir Godot.

P3.4 Auto-regenerar physics_sha256 del manifest
  - En build_windows.ps1, tras copiar DLLs, recalcular el SHA256 del JSON de
    fisica y actualizar physics_sha256 en el manifest.json afectado para que
    no derive.

================================================================================
4. RIESGOS / NOTAS
================================================================================

- P0.1 toca SConstruct y los build.rs: conservar el fallback a
  `git rev-parse HEAD` para que builds fuera de CI (invocando scons/cargo
  directo) sigan funcionando.
- El gate runtime FATAL se mantiene como backstop; con P0.1 no deberia
  dispararse nunca.
- check_runtime_parity.ps1 es suficiente verificando HEAD == BUILD_SOURCE
  (gracias a P0.1 todos los DLL comparten ese SHA); no hace falta invocar
  exports de DLL desde PowerShell.
- Verificar que el cambio de env-var no rompa bootstrap_windows.ps1 ni
  pipelines que llamen a scons/cargo directamente (usaran el fallback git).
- Mantener el principio RUNTIME PARITY del AGENTS.md: el runtime debe
  rechazar binarios cuyo BUILD no coincida con HEAD; P0 lo hace fallar
  rapido y ANTES del launch, no como FATAL silencioso dentro de Godot.
