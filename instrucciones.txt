4. DECISIONES DE ARQUITECTURA
===============================================================================

4.1 Configuración raw frente a configuración resuelta
----------------------------------------------------

No seguir ampliando `SoundConfig` con valores centinela. Separar:

- `RawSoundConfig`: campos `Option<T>` provenientes de JSON.
- `ResolvedSoundConfig`: todos los campos concretos, saneados y listos para DSP.
- `ResolvedMixerConfig`: mapa completo por bank key, buses compilados y master.

Resolución:

  built-in safe defaults
      <- defaults del JSON
      <- override del sonido
      <- sanitización/validación cruzada

El resolver debe recibir las claves reales del banco para producir configuración
efectiva incluso para sonidos no listados explícitamente.

No usar comparaciones como `volume != 1.0` para inferir presencia. Un JSON que diga
`volume: 1.0` es un override explícito válido.

4.2 Diagnósticos estructurados
------------------------------

Crear un resultado común:

  ConfigLoadResult {
      resolved,
      warnings,
      errors,
      source_hash,
      schema_version
  }

Contratos:

- Archivo ausente: defaults seguros + warning identificable.
- JSON malformado: conservar último snapshot válido; en arranque usar defaults.
- Clave desconocida: warning con ruta JSON; ignorar la clave.
- Bus inexistente: warning/error configurable y send desactivado en el snapshot.
- Valor fuera de rango: warning + clamp documentado.
- Valor no finito: error/default seguro. Recordar que JSON estándar no serializa
  NaN/Inf; cubrir construcción programática y formatos inválidos en tests.

`va_validate` debe llamar al mismo resolver que el runtime. No duplicar reglas.

4.3 Estado DSP por voz
----------------------

La configuración es inmutable por snapshot; el estado mutable vive por voz:

- Cursor/resampler existente.
- ADSR state y nivel.
- Biquads L/R o mono pre-pan según la etapa.
- Estado tube/DC blocker si se requiere.
- Ganancia/pan suavizados.
- Identificador del bus de reverb precompilado; no buscar strings por sample.

Loops engine/exhaust/bed/scrape necesitan una strip persistente por clave.
One-shots necesitan un pool fijo de voces; no reiniciar una voz ocupada sin una
política explícita y probada (free -> oldest/releasing -> reject).

4.4 Render real-time safe
-------------------------

Fuera de `render()`:

- Lectura de archivos y timestamps.
- Parseo JSON y validación.
- Creación de filtros, buffers de delay y tablas.
- Resolución de strings a índices.
- Construcción del snapshot y preparación del crossfade.

Dentro de `render()`:

- Solo memoria preasignada, índices y aritmética acotada.
- No filesystem, locks, canales bloqueantes, logging ni crecimiento de Vec/Map.
- Intercambio de snapshot en frontera de bloque mediante mecanismo wait-free o
  controlado por el owner thread antes de invocar render.

SPRINT 1 — PRIMITIVAS DSP AISLADAS (P0)
---------------------------------------

Crear módulos independientes bajo `src/dsp/`:

  adsr.rs
  biquad.rs
  eq.rs
  pan.rs
  tube.rs
  reverb.rs

S1-1 ADSR:

- Estados Idle, Attack, Decay, Sustain, Release y Done.
- Tiempos convertidos a samples al preparar config.
- Curvas linear, exponential y logarithmic monotónicas y finitas.
- `note_off` de loop preserva cursor durante release.
- One-shot inicia release a tiempo para acabar sin corte.
- Cero división por cero cuando un tiempo es 0 ms.

S1-2 Biquad/EQ:

- Peaking EQ estable para 31..16000 Hz, limitado por Nyquist.
- Coeficientes calculados fuera de render.
- Diez bandas en cascada, bypass transparente cuando disabled/0 dB.
- Protección de denormals y reset determinista.
- Suavizado/crossfade de coeficientes al cambiar snapshot.

S1-3 Pan:

- Equal-power exacto:
    L = cos((pan + 1) * PI / 4)
    R = sin((pan + 1) * PI / 4)
- Tests en -1, 0, +1 y conservación de potencia.

S1-4 Tube:

- Parámetros configurables por sonido: enabled, amount, boost_link, bias, mix y
  auto_gain; resolverlos fuera de render y conservarlos en el snapshot DSP.
- Drive efectivo basado únicamente en boosts positivos normalizados.
- Bias, saturación suave, dry/wet y compensación de ganancia.
- Remover DC introducido por bias antes de salida.
- enabled=false debe efectuar bypass transparente bit a bit o con tolerancia
  explícita; mix=0.0 conserva la ruta dry y amount=0.0 no introduce color.
- Tests separados deben demostrar efecto medible activo y transparencia en bypass.

S1-5 Reverb:

- Implementación estéreo determinista FDN o Schroeder.
- Buffers preasignados; pre-delay, decay/RT60, damping, low/high cut y width.
- Clamp de delays para evitar cero/modulo inválido.
- Tail continúa aunque no haya sends activos.
- Reset y cambio de sample rate probados.

S1-6 Limiter master:

- Estéreo enlazado: un pico en un canal aplica la misma reducción a ambos.
- Ceiling configurable y finite guard.
- Definir si es soft saturator + ceiling o limiter con envelope; documentarlo con
  precisión. No llamar “limiter” a una función que solo multiplica `tanh`.

Gate S1:

- Respuesta EQ medida en centros y bandas vecinas.
- RT60 aproximado dentro de tolerancia definida (por ejemplo ±15%).
- Pan conserva potencia dentro de 1e-5.
- Ningún test produce NaN/Inf/denormal persistente.
- Benchmark aislado demuestra cero allocations por bloque.

Métricas mínimas sugeridas (ajustar mediante baseline, no inventar al final):

- Peak absoluto <= limiter_threshold + 1e-5.
- NaN/Inf = 0.
- DC post-master acotado por test de señal silenciosa/bias.
- Pan center: L/R iguales dentro de 1e-5 para fuente mono sin reverb.
- Equal-power: L^2 + R^2 constante dentro de 1e-5.
- Bypass DSP: error máximo y RMS declarados explícitamente.
- RT60 medido con tolerancia antes de aprobar presets.
- Allocations en render: 0 después de warm-up.
- Tiempo de peor bloque: medir p50/p95/p99; objetivo inicial <10% de un core a
  44.1 kHz, pero registrar hardware y tamaño de bloque.

No usar solamente “tests pasan”. Cada feature DSP necesita un test que demuestre
que cambia la señal cuando está enabled y que es transparente cuando está disabled.
